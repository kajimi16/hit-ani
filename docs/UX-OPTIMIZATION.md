# 体验优化清单（实测版）

> 每一条都有**实测证据**，不是通用建议。按「用户可感知的收益 ÷ 成本」排序。
> 未实测的推测不写进来。

---

## 一、实测发现的真问题

### 1. 没有自定义 404 页 —— 用户看到英文报错

```
实测 /definitely-missing-page  →  HTTP 404
正文：404: This page could not be found.
```

没有 `src/app/not-found.tsx`，用的是 Next 默认页：**英文、无导航、无品牌**。
`/users/{不存在的 id}` 也走它。

**为什么会碰到**：学生从聊天记录点了一个已被删除的条目链接。

**做法**：`src/app/not-found.tsx` —— 一句中文说明 + 「回到探索」按钮 +
搜索框。成本极低，收益直接可见。

---

### 2. 没有错误边界 —— 页面出错变白屏

没有 `error.tsx` / `global-error.tsx`。生产环境下页面抛错时 Next 显示
**裸的错误页**（英文，无导航）。

**为什么本项目容易碰到**：详情页、时间表、人物页都依赖外部（Bangumi、
Jellyfin、第三方源），失败面比纯静态站大得多 —— 而 `enrichSubject` 这类
调用已经有 `.catch()`，但**渲染层的意外**（例如某个字段形状变了）没有兜底。

**做法**：`src/app/error.tsx`（客户端组件，提供 `reset()`）+ 各关键路由的
局部 `error.tsx`。文案给出「重试」与「回到上一页」两个出口。

---

### 3. 详情页 338 KB，其中 65 张图片占 140 KB

```
实测 /subjects/493016
  总大小        338 KB
  <script>      121 KB
  去掉 script   218 KB
  <img> 65 个   140 KB      ← 主要构成
  srcset 条目   1036 条
```

**根因：制作人员默认只显示 12 位，但 180 位全部渲染进了初始 HTML。**

```tsx
// subject-aside.tsx
{staff.slice(0, STAFF_PREVIEW_COUNT).map(renderStaffItem)}   // 12 位
<details>
  {staff.slice(STAFF_PREVIEW_COUNT).map(renderStaffItem)}     // 另外 168 位，也在 HTML 里
</details>
```

`<details>` 只是 CSS 隐藏 —— 那 168 行的标记仍然要传输与解析。
实测 HTML 里有 **59 个 staff 头像 `<img>`**。

**把开销拆开看**（避免修错地方）：

```
<img> 标签合计      140 KB
  其中 srcSet 属性   122 KB   ← 纯标记重量，**不产生网络请求**
  其余（src/class…）  17 KB
```

也就是：
- **网络请求没有浪费** —— 图片**已经带 `loading="lazy"`**（实测 59/59），
  折叠区里的图不会去拉。
- 真正的浪费是 **`srcSet` 的候选尺寸**：Next 默认给出 16 个候选
  （`deviceSizes` 8 个 + `imageSizes` 8 个），而一个渲染宽度 32px 的头像
  根本用不到 3840w —— 它却要为这 16 个候选各写一段 URL。

**做法（最省事、收益明确）**：收窄 `next.config.ts` 的候选尺寸。
本站实际最大渲染是详情页封面 340px（2x = 680），因此 1200/2048/3840
这些档位永远用不到：

```ts
images: {
  deviceSizes: [384, 640, 828, 1080, 1920],
  imageSizes: [16, 32, 48, 64, 96, 128, 256],
}
```

候选从 16 降到 12，`srcSet` 重量直接少 25%，且**不影响任何实际显示尺寸**。

若还想更彻底，再考虑「折叠区不 SSR」（需要给制作人员加一个轻接口），
但那要动数据流，收益不如上面这条直接。

### 4. 图片加载时是空白 —— 没有模糊占位

全站没有 `placeholder="blur"`。封面从 `/_next/image` 加载期间，卡片里是
**一块纯背景色**。

局域网内封面已缓存（实测优化器命中 1–2ms），所以首屏不痛；但：
- 新条目的封面第一次请求要回源 BGM（实测网络抖动时会失败）；
- 制作人员/相关人物列表一屏几十张图，会看到明显的「逐个亮起」。

**做法**：BGM 封面是 JPG/PNG，`blurDataURL` 需要服务端生成 —— 不值得为它
引入依赖。**更划算的替代**：给图片容器一个**骨架微光**（已有 `.shimmer`），
加载完成后淡入。这比模糊占位实现简单得多，视觉收益接近。

---

### 5. 屏幕阅读器不知道「加载完了」

全站只有 3 处 `aria-live` / `role="status"`（`inline-confirm`、
`oauth-notice-banner`、`loading`）。而**客户端拉取**的地方不少：
评论列表、外部资源、Jellyfin 媒体库、好友搜索。

**表现得像**：视障用户点了「加载更多」，界面变了但没有任何播报。

**做法**：给这些容器的状态提示加 `role="status"`（`加载中` / `已显示 N/M`
/ `加载失败`）。改动是加属性，成本极低。

---

### 6. 客户端组件比例高 —— 但**没有一个是可拆的**

```
实测：src/components 下 31 个组件，25 个带 "use client"
详情页首屏挂了 6 个客户端组件
```

**本条最初写的是**「`library-views.tsx` 没有任何交互却被算作客户端组件」——
**那是错的**（经外部审查指出后实测确认）：`library-views.tsx` **没有
`"use client"`**，它本来就是服务端组件，两个消费者（`/library`、
`/users/[id]`）也都是服务端组件。

逐个核对 25 个客户端组件的**交互点**（`useState` / `useEffect` / `onClick` /
`fetch` / `usePathname` / `useSyncExternalStore`）后：

```
真正无交互的客户端组件：0 个
```

连看起来最「纯」的两个也有理由：
- `user-avatar.tsx` —— 需要 `onError` 做加载失败回退；
- `side-nav.tsx` —— 需要 `usePathname` 做当前页高亮。

**结论：这条不构成可执行的优化项，已降级为「现状说明」。**
要真正降低首屏 hydration，需要把「服务端取数 + 客户端小岛」的边界重新划一遍
（例如把 `video-player` 拆成「服务端外壳 + 客户端岛屿」），那是重构级的工作量，
不是「顺手拆几个组件」。

**这也说明**：清单里「每个文件都点开确认过」这个标准要**真的执行**——
本条第一版是凭印象写的（看到「30 个组件 24 个客户端」就推断其中必有纯展示的），
而与实测相反。

## 二、已经做得好的（别动）

| 项 | 证据 |
|---|---|
| 键盘焦点可见 | `:focus-visible` 是**全局**定义（`globals.css:219`），不是零散补的 |
| 加载骨架 | `src/app/loading.tsx`，且复用真实网格类保证不跳版 |
| 减少动效 | CSS 的 `@media` + `scroll-row.tsx` 的 JS 判断，**两层都覆盖** |
| 对比度 | WCAG AA 有回归测试（`tests/contrast.test.ts`），含 M3 全部角色配对 |
| 大列表分页 | 追番页（1168KB → 115KB）、评论区（50 条 → 2 条 + 加载更多） |
| 弹幕可读性 | 按背景计算对比度，实测修正 343 条不可读弹幕 |

## 三、可选的「设计感」增强（非缺陷，纯加分）

按用户会注意到的顺序：

1. **Hero 轮播的进度指示** —— 现在自动轮播每 6 秒推进，但看不出「下一张什么时候来」。
   一排小圆点 + 当前项的高亮进度条即可。
2. **卡片 hover 的层次** —— 目前只有遮罩变亮。可加极轻微的 `translateY(-2px)`
   （已有 `.lift` 类，只差应用）。
3. **空状态的插画** —— 现在全是纯文字（「还没有想看的番」）。一个简单的
   SVG 占位能让空页面不那么像出错。
4. **数字的等宽对齐** —— 排行榜/统计已用 `font-mono`，但追番卡片上的
   「0/13 集」没有，多行列表里会对不齐。
5. **深色主题的图片降亮** —— 深色界面里纯白封面很刺眼。可给封面加
   `filter: brightness(0.92)`，让整体更协调。

## 四、不建议做的

| 项 | 原因 |
|---|---|
| 骨架屏铺满每个客户端组件 | 现有 `loading.tsx` 已覆盖路由级；组件级骨架在局域网下会「闪一下就没」，比不显示更烦 |
| 引入 UI 组件库 | 现有设计系统已对齐 Animeko 的 M3，引入第二套约定会让界面分裂 |
| 全局 `placeholder="blur"` | 需要为每张 BGM 封面生成 blurDataURL，收益不抵复杂度（见 4） |
| 虚拟滚动 | 追番页与评论区已分页，量级不构成瓶颈；过早优化会增加滚动相关的 bug 面 |

---

## 五、建议的执行顺序

| # | 事项 | 成本 | 用户可感知 |
|---|---|---|---|
| 1 | 自定义 404 + 错误边界 | 低 | 高（出错时的观感完全改变） |
| 2 | 收窄 `next.config.ts` 的图片候选尺寸 | 低 | 中（详情页 srcSet 少 25%，且不影响显示） |
| 3 | `role="status"` 补齐 | 低 | 中（无障碍） |
| 4 | 图片骨架微光 + 淡入 | 低 | 中（首屏观感） |
| 5 | 拆分纯展示组件为服务端组件 | 中 | 低（bundle/hydration） |
| 6 | Hero 轮播进度指示 | 低 | 中（设计感） |

1–4 都是「改动小、可见」的类型，适合一次做完。
