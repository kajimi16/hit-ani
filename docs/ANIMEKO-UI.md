## 0. 一句话结论

**Animeko 是「客户端播放器」，我们是「校内社区 + 索引站」。**

它在**播放侧**（BT 边下边播、多源自动选择、播放器控件、弹幕样式）远超我们，
而且其中相当一部分**纯 Web 做不到**（需要 libtorrent、本地文件系统、原生播放内核）。

我们在**社区侧**（校内弹幕/评论筛选、时光机、多源弹幕合并、无障碍与可读性）
有它没有的东西。

所以「对齐 Animeko」不是目标 —— 该做的是：**补齐它在 Web 上做得到、而我们确实缺的**，
并**继续加固我们的差异化部分**。

#### 评分有两套，但只有一套有界面（核实后新增）

本项目有**两个**评分字段，语义与可用性不同：

| 字段 | 谁在写 | 有无 UI |
|---|---|---|
| `Collection.rating` | 只从 Bangumi 导入（`import.ts`）/ `POST /api/collections` 接受 | ❌ **没有界面能设置它** |
| `Review.rating` | 评价表单（`review-panel.tsx`） | ✅ |

也就是说：**用户无法「只打分不写评论」** —— 而那恰恰是 Bangumi 站内最常见的动作
（收藏时顺手打个分）。`collection-picker.tsx` 只处理五种状态，不含评分。

Animeko 那边评分是收藏的属性（`updateRating`，需先收藏），与评论分离且有 UI。
这一项我方是**真实缺口**，且成本很低（字段与 API 都已就绪，只差界面）。

## 2. 缺口分类

### A. 该补：Web 做得到，且实用（按性价比排序）

1. **播放器控件自绘**（最大的一处短板）
   现在用原生 `controls` —— 意味着**播放器体验完全由浏览器决定**，与「像 Animeko」
   差得最远。可做：倍速（含快捷键）、键盘快捷键、双击全屏、横滑 seek、
   自动连播、跳过 OP/ED（若 Jellyfin 给章节）。记忆播放位置需先定 schema。
2. **弹幕样式设置**（字号/透明度/显示区域/开关类型）
   现在**全是硬编码常量**。改成设置项成本低、收益直观 —— 尤其「字号」在
   小屏上几乎是必需的。
3. **人物页 / 角色页**
   Bangumi v0 有 `/v0/persons/{id}`、`/v0/characters/{id}`、`/characters/{id}/subjects`、
   `/persons/{id}/subjects`，我们的 `schema.d.ts` **已生成对应类型**，只是没接。
   条目页现在只有 12 位制作人员，点不进去。
4. **关联作品板块**
   `/v0/subjects/{id}/subjects` 可用。看「同系列还有哪些」是高频需求。
5. **收藏评分界面（只打分不写评论）**
   字段与 API 都已就绪（`Collection.rating`、`POST /api/collections` 接受）
   —— 只差一个界面。这是**成本最低的一项**，而缺失它意味着用户必须写一段
   评论才能打分。
6. **搜索增强**：年份/季度 chip、搜索历史（localStorage）、输入联想。
7. **观看记录 + 续播** —— ✅ **已实现**
   加了 `Collection.playbackPositionMs`（条目级，不是每集一行 —— 一部番同一时刻
   只会在一个位置继续看）。**只服务外站源那条路径**：Jellyfin 自己维护
   `PlaybackPositionTicks` 且跨设备同步，本地再存一份只会两边打架。
   位置上报与观看状态**解耦**（`PUT /api/progress` 的 `type` 改为可选），
   服务端独立钳制上报值（客户端可篡改）。追番列表回显「上次看到 mm:ss」。
8. **弹幕单源开关与时间偏移**
   多源合并后，「这个源对不上」是常见问题；`shiftMillis` 是廉价解法。

### B. 该继续加固：我们的差异化

1. **校内维度**（弹幕/评论/时光机）—— 这是存在理由，应继续做深：
   校内排行榜、班级/年级维度、按学校的评论聚合。
2. **弹幕可读性**（按背景计算对比度）—— Animeko 只做「禁用彩色」，我们做对了。
   可进一步：让用户能覆盖（万一他就想要原色）。
3. **无障碍**（`prefers-reduced-motion`、对比度测试、键盘可达）——
   Animeko 的 Compose 侧没有这些约束（那是 Web 特有的）。
4. **举报处理后台**（B2）—— 我们现在只有写入，没有读取路径。

### C. 明确不做：纯 Web 不可行或与约束冲突

| 项 | 原因 |
|---|---|
| BT / 磁力边下边播 | 需 libtorrent、随机读写、DHT |
| 离线下载 / 缓存管理 | 需本地磁盘；且**校内带宽不允许**（`docs/MEDIA.md` §6.2 已否决） |
| 原生播放内核（mpv/ExoPlayer） | 浏览器只有 MSE/WebCodecs |
| GPU 画质增强 | 需 shader 管线 |
| HLS 广告过滤代理 | CORS |
| 系统级（亮度/刷新率/相册/系统分享） | 浏览器无对应 API |
| 系列关系图 | 依赖 Animeko 自建后端，Bangumi v0 不提供 |
| 讨论区 | **Animeko 自己也是占位**（`subject_details_coming_soon`） |

### D. 做得比 Animeko 好的地方（已有，别丢）

- 收藏排序（4 种，含空值位置处理）—— 它没有排序
- 弹幕颜色可读性 —— 它只是「禁用彩色」
- 时光机、时间表排行榜、QQ 绑定、上游写入闸门与审计
- 无障碍：`prefers-reduced-motion`（含 JS 侧）、对比度回归测试

## 4. 与「校内自建」这个前提的关系

Animeko 是面向个人的客户端，功能取舍围绕「一个人看得爽」。
我们是校内平台，取舍应围绕「一群人在同一所学校里一起看」：

- 它把弹幕当**播放器附属品**；我们把它当**社区内容**（本校筛选、举报、屏蔽词）。
- 它没有服务端内容治理；我们必须有（UGC 平台的责任）。
- 它的「推荐」是算法；我们的榜单是**校内真实观看数据**（时光机/排行榜）。

因此上面 A 类该补，但**不应为了像它而牺牲 B 类**。
